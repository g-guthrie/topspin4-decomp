## 1. How skills work (V)

* **Definition.** A skill is a code string, for example `PoisonedSlices`. Its id is `zlib.crc32(code)`.
  The name and the description are StringTable entries with keys `crc32("Ability<Code>Name")` and
  `crc32("Ability<Code>Text")`. There are 32 such strings. 30 of them are skills in the State.bin
  template `PlayerState.Profile.SkillList`. The other two (Return6thSense, EmergencyReactivity) are
  strings only.
* **In-match storage.** The skill list is at `PlayerState+0x640`. It holds `{Id, Value}` pairs, and
  Value 1.0 means the player owns the skill. `HasSkill` (`fn_8868F0D8`) scans the list for the id
  with Value == 1.0. The first four owned entries become Skill1..4 (`fn_8869DEF0`).
* **Sources.**
  * Pros: `PlayerList.bin` `AttributeList.Skill1..4`. 731 players are listed. Some Skill slots hold
    attribute-bonus keys rather than skills.
  * Created players: coaches, through `CoachList.bin` abilities. A silver coach grants 1 skill and a
    gold coach grants 2. A skill becomes active at its `unlock_step` (= `Ability.Efficiency`, 0..4):
    the number of the coach's four objectives completed. The career native
    `UpdateActiveCoachSkills` (`0x88853790 -> fn_88852CB0`) applies them (see `stats-coaches-career.md`).
  * Level/style tracks (`PlayerEvolution.bin`) give attribute points only, no skills (V: no skill keys
    in the packs).
* **Consumers.** Each skill acts in one of two ways:
  1. **Analyser graph link ports.** 28 skills are read as `Profile.SkillList[Id].Value` by
     `Expressions.bin` graphs. Since Value is 0 or 1, a graph either multiplies a bonus by it
     (`product(skill, k)`) or selects an alternative curve with it (`lerp(a, b, skill)`).
  2. **Code tests.** Three skills are tested in code: PoisonedSlices, InstantRocket and
     SpectacularVolleys. A fourth id, Fatality, also appears in code, but as a swing-category id.
* **Outputs touched.** Every graph effect lands in the shot-quality outputs of the shot-class graphs.
  These are listed in `graphs-decoded.md` s4:

  | output | offset |
  |---|---|
  | `ReceiverState.AimingState.Efficiency` | S+0xD88 |
  | `DeepDeviation` | S+0xD78 |
  | `OutEfficiency` | S+0xD8C |
  | `7e28dbc0.FaultProbability` | S+0x718 |
  | `7e28dbc0.PowerfulFactor` | S+0x778 |
  | `9c11fa39.ControlValues` (power/aim/fault mixes) | S+0x10..0x1C of that block |

  Inside each aiming graph most bonuses are summed and then clamped by a curve, typically
  `[0..0.3: 0 -> 0.3]` (graph 188 `curve41`). So several stacked skills cannot add more than +0.3 to
  that sum.

### 1.1 For G3b (ball)

**No skill writes a ball-physics or template parameter directly (V).** All 30 skills reach the ball
only through the per-shot analyser outputs above. Those outputs feed shot evaluation and the
ball-target deviation:

* `PowerfulFactor` S+0x778 sets the speed mix.
* `AimingState.Efficiency` / `DeepDeviation` S+0xD88 / S+0xD78 set the target scatter in cm.
* `FaultProbability` S+0x718 sets the net/out decision.
* `OutEfficiency` S+0xD8C.

The exact template fields fed by these outputs are G3/G3b's mapping (`shot-to-template.md`). This note
gives only the skill-side deltas.

The two code-level effects that come closest to the ball:

* **PoisonedSlices** sets a flag on the *receiver* (S+0x7D0). The receiver's shot graphs then read it,
  so the ball the owner hits is unchanged. The penalty applies to the reply.
* **InstantRocket** changes the power-charge curve (S+0xE00 / S+0xE08). That is a shot-input value,
  not a ball parameter.
