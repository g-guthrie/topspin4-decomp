# How Swing_DLL was compiled, and the LTCG matching route

LT1, 2026-11-14. Every claim below comes with the command that reproduces it. Scratch outputs live in
`work/` (git-ignored). No game bytes are committed.

## 1. Answer

- **Yes, /GL and /LTCG were used.** The PE Rich header lists 362 objects whose code was generated at link time
  (`Utc1600_LTCG`, prodid 0xAF, build 10224). They sit next to 1,236 plain C++ objects, 326 plain C objects and
  212 objects from an older VC9-era compiler (build 8153). No profile-guided-optimisation prodids appear, so
  PGO was **not** used.
- **The game code is the LTCG part.** Callers keep volatile registers live across calls into functions several
  megabytes away, in other subsystems. Only a whole-program code generator can do that. The prebuilt libraries
  (FMOD, Havok, D3DX, XDK) show none of it.
- **The game project also used `/Oc`** ("disable divide-by-zero exceptions"). Across 0x885F4E48-0x889CE000,
  the binary has 0 trapped divides and 1,081 untrapped divw/divwu sites. This one flag removes the
  "divide without twllei" blocker, and it works on the plain route too.
- **Floats: `/fp:precise`.** The ±1-table `fsel`/`mfcr` lowering appears only with an explicit `/fp:precise`;
  this compiler's default never emits `mfcr`. Its table lives in an LTCG constant pool (`__pool@`).
- **We can reproduce it.** `tools/fn_check_ltcg.py` compiles with /GL, links with the original
  `link.exe /LTCG`, extracts the linked function and compares it. Two previously blocked functions now match
  only this way:
  - `0x8864BE20`: 316 bytes, gameplay window;
  - `0x889CE9E0`: Lua `auxsort`, 860 bytes.

  zlib `deflate` (0x88876730) goes from 135 differing instructions to 4.
- **Integration** needs four lines in `tools/matching.py` plus small hooks in the integration tools
  (`docs/ltcg-route-pipeline.patch`, design in section 6). The coordinator applied it in commit `cb9135a`,
  and matching run b43 verified the first LTCG unit (`ga6_ltcg_b.c`).

## 3. Evidence from the binary

### 3.1 Rich header (decisive)

Command: parse the `DanS`…`Rich` block at file offset 0x80 of the PE (XOR key at `Rich`+4). The script is
in section 8.

| prodid | build | count | meaning |
|---|---:|---:|---|
| 0x00AF | 10224 | **362** | Utc1600_LTCG: compiled with /GL, code generated by link.exe |
| 0x00AB | 10224 | 1,236 | Utc1600_CPP: plain C++ |
| 0x00AA | 10224 | 326 | Utc1600_C: plain C |
| 0x0084 / 0x0083 | 8153 | 158 / 54 | Utc1500 C++ / C (older compiler: prebuilt libraries) |
| 0x009E | 10224 | 25 | MASM 10 |
| 0x009B / 0x009D / 0x009C | 10224 | 1 / 1 / 3 | Export / Linker / Implib |
| 0x007B / 0x006D | 2909 | 2 / 1 | VC8 implib / C |
| 0x0001 | 0 | 378 | imports |

**Calibration.** Linking our own objects with the same link.exe (`work/ltcg-toolchain`) gives:

- /GL C++ → 0xAF;
- /GL C on its own → 0xAE;
- /GL C linked together with /GL C++ → counted under 0xAF;
- plain C → 0xAA;
- plain C++ → 0xAB.

So the 362 can include C objects compiled with /GL. There are no 0xB1-0xB4 (POGO) entries.

The XEX static-library header (key 0x000200FF) also lists `D3D9LTCG 2.0.20209.16387`, the /GL build of the
D3D runtime, along with `LINK 10.0.10224`, `C1`/`C2 16.0.10224`. The `C1`/`C2` entries come from the
`.XBLD` records of any object, so on their own they do not prove LTCG.

### 3.2 Cross-subsystem register knowledge (where the LTCG code is)

`work/…/readr.py` (scratch) flags a caller that reads a volatile register (r0, r4-r12, f0, f2-f13) after a
`bl` without writing it first. It skips `__save*`/`__rest*` and the `mr rX,rX` marker. A violation inside
one object can be the plain compiler's private convention for `static` functions. A violation where callee
and caller lie in **different subsystems** can only come from LTCG.

Cross-subsystem hits by caller bucket:

| Bucket | Hits | Callee buckets |
|---|---:|---|
| game core 0x88150000-0x88287D28 | 21 | Pam core, gameplay, UI, renderer, physics wrapper, Lua glue |
| Pam core 0x885F4E48 | 65 | gameplay, game core, physics wrapper |
| gameplay 0x88640000 | 8 | game core, front end, physics wrapper |
| renderer 0x886E8000 | 16 | Pam core, UI, gameplay, game core, physics, D3D9 |
| UI/script 0x88780000 | 18 | renderer, Pam core, ball, core, flow DB, physics, D3D9 |
| flow DB 0x8883C000 | 18 | ball, front end, physics |
| ball/camera 0x888AA8D0 | 5 | UI, physics, Havok glue, Lua glue, D3D9 |
| front end 0x88900000 | 61 | Pam core, UI, gameplay, ball, physics, D3D9 |
| FMOD, Havok, CRT, XAudio | 1-19 each | only assembly helpers (`_RtlCheckStack12`, CRT stubs): not evidence |

Two worked examples:

- `0x8816C490` (game core) loads r8 and r9 before a loop and keeps them across
  `bl ts4_index_to_name_hash_887F7BC8`, which is 6.8 MB away.
- `0x8864BE20` (gameplay) keeps r6 across `bl ts4_msg_pool_service_get_8864DFF0`, and r4 across
  `bl ts4_blowfish_encrypt_ecb_88605220`.

### 3.3 Divide traps: the `/Oc` flag

`cl.exe /?` for 16.00.10224 lists `/Oc disable divide-by-zero exceptions`. With it, `a/b` compiles to a bare
`divw`. Without it, the compiler emits `divw; twllei rB,0; twlgei …`.

Census of every divw/divwu in the image, counting a site as trapped when a `tw`/`twi` lies within 4 words:

| Range | untrapped | trapped |
|---|---:|---:|
| game core 0x88150000-0x88287D28 | 1,041 | 42 |
| D3D9/PIX/D3DX/png | 67 | 158 |
| FMOD + codecs | 190 | 296 |
| Havok (all) | 46 | 65 |
| CRT/xapi, XAudio2 | 229 | 71 |
| **0x885F4E48-0x889CE000 (game, Lua core, zlib 1.2.3, expat)** | **1,081** | **0** |
| trio | 0 | 6 |
| Lua libs 0x889CE000 | 0 | 4 |

The trapped sites inside game core are probably embedded third-party code.

### 3.4 Constant pools

LTCG merges a module's float literals into `__pool@_N` blocks addressed as base plus offset. Plain objects
use one `__real@XXXXXXXX` COMDAT per value. In the target, `g_ts4_script_constants` (0x880D0F70, 0xA70 bytes)
is such a pool. For example, the ±1 table at +0x68 is reached through `addi r11,pool; addi r8,r11,0x68`.
This reproduces only under LTCG; PC1's static-array trick imitates it on the plain route.

### 3.5 Link order

In our LTCG links, link.exe places all LTCG code first, then the plain objects in command-line order.
Swing has two LTCG-looking blocks:

- 0x88150000-0x882A0000;
- 0x885F4E48-0x889D3410.

The prebuilt libraries lie between them. The original build therefore had more structure than a single
`link /LTCG` of loose objects: libraries, section names or `/ORDER`. That structure is not reconstructed
here. It does not affect per-function matching.

**Flags that fit the evidence:**

- `/O2 /Oi /Oc /GL`, plus `/fp:precise` for float code;
- link with `/LTCG`.

`/Ox`, `/fp:fast` and `/fp:strict` do not fit:

- `/fp:fast` and the default never give the ±1 table;
- `/fp:strict` gives the same table as `/fp:precise` on 0x886A48B8. GA3 reports that it brings 0x88682290
  to within about 20 instructions. Whether `/fp:strict` or `/fp:precise` is the project setting is untested.

## 6. Integration design (the patch for tools/matching.py)

`tools/ltcg_route.py` (new) holds everything; `docs/ltcg-route-pipeline.patch` wires it in.

1. **Spec.** Same format as HS1, plus:
   ```json
   {"source": "src/xbox360/lt1_x.c", "route": "ltcg",
    "context": ["src/xbox360/callee.c", "flags(/Ob1):src/xbox360/other.cpp", "nogl:src/xbox360/lib.c"],
    "include": ["callee_with_other_callers"], "no_include": false,
    "flags": ["/Oc"], "functions": {...}, "renames": {...}}
   ```
2. **integrate_match.py.** A spec with `"route": "ltcg"` updates symbols, splits and objects.json exactly like
   a plain spec. It is recorded in `config/54540859/ltcg_units.json` through `ltcg_route.register()` instead
   of `MATCHING_UNITS`.
3. **matching.py** (4 lines):
   - `import ltcg_route`;
   - `ltcg_route.add_arguments(parser)`, which adds `--ltcg-wibo`, `--ltcg-toolchain` and
     `--ltcg-target-image`, all with defaults;
   - `rebuilt_by_source.update(ltcg_route.build(args, rebuilt_dir, split_dir, symbols, xex))` after the
     plain compiles;
   - `expected.update(ltcg_route.expected_symbols())` in `verify_report`.

   `build()` runs the same compile, link, extract and compare as `fn_check_ltcg.py` for each unit. It stops
   the build on any mismatch or unapplied rename. Then it writes the rebuilt object: the unit's split object
   with each function's code replaced by **our linked bytes**. Relocation fields keep the split's bits,
   because a linked image has none, and it refuses if any other bit differs. objdiff, `verify_report`,
   match.json, sync_progress and the decomp.dev report then treat the unit like any other.

   With no `ltcg_units.json`, all four hooks do nothing, so the plain route is byte-for-byte unchanged.
4. **sync_progress.py / link_probe.py** iterate `ltcg_route.all_units(MATCHING_UNITS)`, so LTCG units count
   in match.json and progress and enter the link probe.
5. **Requirements on the matching machine:**
   - the PR110 wibo;
   - `python3 tools/fn_check_ltcg.py --setup` (copies the compiler to `work/ltcg-toolchain` and builds the
     OLEAUT32 stub with mingw);
   - `orig/54540859/Swing_DLL.dll`, read only when a pooled constant is compared by value.
6. **Tested:**
   - `tests/test_ltcg_route.py` and `tests/test_fn_check_ltcg.py` use synthetic input;
   - a dry run of `build_units` on the integrated plain unit `gp2_swing_wrappers.c` (10 functions) against
     `work/matching-b41` produced an object byte-identical to its split;
   - the patched tools compile, and `matching.py --help` shows the new options. `git apply --check` passes.

**Policy points for the owner:**

- A POOL acceptance compares the constant's value, not its address. The original pool layout is a
  whole-program artefact we cannot reproduce in a scratch link.
- Context files are compiled into the scratch link but are not counted.
- A context entry may carry per-file flags such as `flags(/Ob1):`. Those flags stand in for inlining
  decisions the original made with the whole program in view.

## 7. How to match with the LTCG route (for agents)

**Setup (once per machine).**
```sh
python3 tools/fn_check_ltcg.py --setup        # work/ltcg-toolchain + OLEAUT32 stub (needs i686-w64-mingw32-gcc)
export TS4_MATCHING_DIR=$PWD/work/matching-b41  # or the newest verified split
```

**Use it when:**
- the function lies in an "ltcg" range of `docs/ltcg-ranges.json`; **and**
- plain `fn_check.py` cannot match it because of one of the following:
  - a register live across a call without being set ("read r");
  - a frame larger than yours;
  - a callee that should not be inlined but is, or should be inlined but is not;
  - `pool+offset` float constants.

**Before that, add `--flags /Oc` on the plain route.** For divides without `twllei` it is all that is needed.

**Command.**
```sh
python3 tools/fn_check_ltcg.py src/xbox360/<you>_x.c name=0xADDR [...] \
  --context src/xbox360/<file defining the callee>.c [--context ...] \
  [--include <callee>] [--flags /Oc] [--flags /fp:precise] [--no-include] [--keep]
```
Output is `MATCH`, `FAIL` with a side-by-side listing, `RENAME` lines (as in fn_check) and `POOL` lines
(constants accepted by value).

**Choosing context files.** Start with `--auto-context` (add `--auto-depth 2` to follow the callees of matched
callees). It reads the target's callees from the original, adds the matched source of each, the contexts recorded
for a callee that is an LTCG unit, the sources of functions the source names but the original does not call
(inlined) and the pool primer last, forces the called callees with `--include`, and prints the contexts, the callees
with no matched source ("missing callee bodies": match those first) and the explicit command. Contexts are compiled
plain; when the link inlines a callee the original calls, the check repeats with `flags(/Ob1):` on that callee's
source. `flags(/Ob1):` on a file keeps the functions *defined in it* from being inlined anywhere, also into each
other: a callee that inlines file-local helpers gets a different body (and clobber set) under it
(0x886C5DB0 matches with w7c_a.c plain and fails with `flags(/Ob1):`). The rules below are what it applies, and what
to add by hand (`--context` values are kept in front):
- Add the file that **defines** each callee whose register use the target relies on. Find the definition
  with `grep -ln "<callee> *([^;]*$" src/xbox360/*`.
- Add the file defining a callee whose noreturn behaviour or frame matters, such as `luaL_error` in
  `lib3_lua_auxlib.c`.
- If LTCG inlines a context function the original calls with `bl`, prefix that file with `flags(/Ob1):`.
- If LTCG changes a context callee's calling convention (an argument goes missing), pass `--include <callee>`.
  In the original that callee had other callers.
- If the **target itself** has a private convention, put its real callers in `--context` and pass
  `--no-include`.
- Keep the context minimal: every extra file is more whole-program behaviour to explain.

**Writing the spec.** Use `work/specs/<ID>/<stem>.json` in the HS1 format, plus `"route": "ltcg"`,
`"context"`, and `"include"` / `"no_include"` when used. Include only functions that MATCH in a final run
of the exact command. `tools/integrate_match.py` records such specs in `config/54540859/ltcg_units.json`.
Say "LTCG route" in your report.

**Pitfalls.**
- Write float literals freely: pooled literals compare by value.
- Do not convert plain matches to this route.
- A FAIL showing `bl` to a stub address that differs from the target is a relocation-target problem, not
  codegen. Check names and placeholders first.

## 10. What the solved blockers unlock (estimate)

Feature scan over all unmatched functions at b41 (scratch `feat.py`, raw-word decode of the PE). Game (ltcg)
ranges: 4,236,476 unmatched bytes. Functions whose **only** flagged blockers are now solved (`read r`,
untrapped divide):

- 1,052 functions, 482,720 bytes;
- 409,568 of those bytes are in functions of 256 bytes or more;
- split: 207 functions / 114,816 bytes with `read r`, 857 / 394,592 bytes with a divide.

This is an **upper bound**. The divide count includes exact pointer-difference divides by a constant in a
register, which were already compilable. Every function also still needs ordinary source work, and the scan
cannot see stack-layout or scheduling problems.
