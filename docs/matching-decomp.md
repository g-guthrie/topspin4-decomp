# Matching-decomp assessment

## Verdict

The repository has a sound clean-room reverse-engineering baseline, but it is not yet a matching decompilation in the sense used by [decomp.dev](https://decomp.dev/) and [dc3-decomp](https://github.com/rjkiv/dc3-decomp). A matching project must compile new C or C++ into code that can be measured against the original binary. Ghidra pseudocode, reviewed symbol names, behavioral equivalence, and successful host-C compilation are useful inputs, but they are not binary-match evidence.

Current matching progress is therefore **zero functions and zero bytes**. The source in `src/xbox360/title_patch.c` is a semantic draft until it is compiled with the identified Xbox 360 compiler and compared in objdiff.

## What is already right

- The exact retail target, module hashes, title ID, media ID, and executable version are locked.
- Game executables, assets, keys, and proprietary SDK material are excluded from Git.
- Local analysis is reproducible, and claims carry addresses, tool versions, and confidence.
- Ghidra output is treated as evidence to review rather than source to publish blindly.
- Updates, DLC, and server-delivered patches are kept separate from the retail baseline.

## What the established Xbox 360 projects add

The four Xbox 360 projects currently listed by decomp.dev are [Dance Central 3](https://github.com/rjkiv/dc3-decomp), [Fallout: New Vegas](https://github.com/ieee802dot11ac/fnv), [Halo Reach](https://github.com/ChimpsAtSea/Reach), and [Sonic the Hedgehog (2006)](https://github.com/rjkiv/sonic06). Their common measurable workflow is:

1. Keep the user-supplied XEX under an ignored `orig/<build>/` directory.
2. Use [Jeff](https://github.com/rjkiv/jeff), the Xbox 360 fork of decomp-toolkit, to infer symbols, relocations, splits, and original COFF objects.
3. Record translation-unit boundaries in `splits.txt` and labels in `symbols.txt`.
4. Compile replacement translation units with the original Xbox 360 MSVC family and flags.
5. Compare original and rebuilt objects with [objdiff](https://github.com/encounter/objdiff).
6. Report only measured object/code matches as progress.

Dance Central 3 is not a representative easy template: its maintainers say their target is a non-LTO debug build with a linker map. Top Spin 4 is a stripped retail build without a known map, so compiler flags and translation-unit boundaries must be recovered rather than assumed.

## Top Spin 4 feasibility probe

Jeff `0.3.5` identified the same toolchain in all three modules:

- linker `10.0.10224.0`
- C1 frontend `16.0.10224.0`
- C2 backend `16.0.10224.0`
- Xbox 360 libraries from XDK `2.0.20209`

This removes the compiler-version guess. It does not establish the original compiler flags.

The initial `xex split` results are mixed:

| Module | Result | Meaning |
| --- | --- | --- |
| `default.xex` | Success | Jeff emitted relocatable COFFs, but the whole `.text` section is still one autogenerated unit. Real source-file boundaries are unknown. |
| `Loader_DLL.xex` | Failed | Function-boundary analysis found overlapping functions near `0x830CF868`. |
| `Swing_DLL.xex` | Failed | Function-slice analysis hit an end-of-section FixedBitSet boundary panic. |

The exact measurements are recorded in `config/toolchain.json`. The failures are tooling/analysis blockers, not evidence that matching is impossible. The correct next sequence is to make Jeff split `Swing_DLL.xex` reliably, establish the first real object boundary, identify compiler flags with small probes, and only then move the semantic draft into an objdiff-backed translation unit.

## Progress gates

A function can advance through these states:

1. **Named** — behavior and address reviewed.
2. **Semantic draft** — clean-room source expresses the observed behavior and passes host checks.
3. **Validated reconstruction** — behavior is checked against a runtime trace or a trusted test oracle.
4. **Matching** — the target compiler output is compared against the original object and meets the declared objdiff threshold.

Only stage 4 contributes to decomp.dev-style matching progress. We should not register this project with decomp.dev until Jeff produces stable splits and an objdiff report exists.
