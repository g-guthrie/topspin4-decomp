## Rule

`link /LTCG` builds **one** float/double pool for the whole program (`__pool@_0`; in Swing it is
`g_ts4_script_constants`, 0x880D0F70, 0xA70 bytes). Entries are deduplicated by (size, bits). Each new entry is
placed first-fit: floats on 4 bytes, doubles 8-aligned, and a later float fills the hole left before a double.
Entries are added in **code-generation order**: leaf functions first, ties in **reverse** command-line /
definition order, callers after their callees. The pool is not split per object and not sorted by size.

So a source that uses every pool entry once, in offset order, reproduces the pool exactly, as long as its
function is generated first. `src/xbox360/pp1_pool_primer.c` is that source. It is generated by
`tools/ltcg_pool_primer.py`, and it **must be the last `--context`**.

### Evidence (each line: one scratch link)

- `exp2.py e2/a.c e2/b.c` (a: 5,6,8; b: 9,6,7,5, both `/INCLUDE`d): the pool is `9 6 7 5 8`. b comes first,
  then a's one new value.
- Same files as `e2/b.c e2/a.c`: the pool is `5 6 8 9 7`.
- `e2/a.c e2/b.c e2/c.c`: c's entries first, then b, then a. c uses `11f 12d 13f 14d 15f 16f 17d` in that
  order, and the pool holds `11f 13f | 12d | 14d | 15f 16f | 17d`: 13f filled the hole at +4.
- One file, `d1` (5,6), `d2` (7,5), `d3` (9, calls d1): the pool is `7 5 6 9`. That is d2 and d1 (the
  leaves, in reverse order), then d3.
- `exp.py src/xbox360/pp1_pool_primer.c`: our pool equals the original's first 0xA70 bytes, with **0 of 668
  words** differing.
- `probe_dis.py pp1_probe.c <primer> e2/w.c` (w.c with 1234.5f, 0.123456f and 30.0f listed **after** the
  primer): 30.0f moves from +0x42c to +0x8. With w.c listed **before** the primer, everything stays in place.

### There are no repeated entries

FP1 counted 0.0 eleven times and 1.0f/-1.0f twice. With each word typed from the code that loads it (lfs =
float, lfd = double, the +0x68 `{1.0f,-1.0f}` select table = one 8-byte constant), the 555 entries have **no
duplicate (size, bits)**:
- the zero words are the low halves of doubles (3.0, 0.5, 16.0, 10.0, …), plus the double 0.0 at +0x58;
- 1.0f at +0 and -1.0f at +0x38 are floats;
- +0x68 is the 8-byte table `3f800000bf800000`.

The table is deduplicated with a double literal of the same bits. The primer writes it as
`pp1_pool_d(0.007812501848093234)`, and FP1's select still lands on +0x68. +0xa54 is an unreferenced zero
word before a double: alignment padding that no later float filled, and the generator skips it.

### Extent

`refscan.py` follows `lis rX,0x880d` → `addi`/D-form chains through every function in `.text`. Pool
references come from the game core (0x88150000-0x882A0000), the LTCG game range (0x885F4E48-0x889D3410)
**and** from plain objects (0x882A0000-0x885F4E48). The plain objects' `__real@` COMDATs resolved into the
pool. The highest scalar reference is `lfd +0xa68` (0x889D2FB8), so the pool ends at +0xA70. Strings follow
from +0xA70 on.

## The generator and the primer

```sh
python3 tools/ltcg_pool_primer.py            # writes src/xbox360/pp1_pool_primer.c (deterministic)
python3 tools/ltcg_pool_primer.py --list     # typed entries: offset, f/d, bits, access kinds
```

- Standard library only. It reads the original image and `config/54540859/symbols.txt` locally, and writes
  no pool bytes, only float literals.
- Output: 555 entries (443 float, 112 double). 525 are typed by an lfs/lfd reference or the table; 30 have no
  reference and are typed as floats (marked `?` in the comment); 1 padding word is skipped.
- Each entry is a call `pp1_pool_f(<literal>f)` / `pp1_pool_d(<literal>)` to an undefined external. The
  checker stubs those without /GL, so nothing folds (`x*1`, `x*2`, `x+0`) and nothing is dropped.
- Float literals are written as the exact decimal value of the float (`0.005999999586492777f`), so cl's
  decimal→double→float conversion cannot round twice. A shortest form such as `3.4028235e+38f` is rejected
  by cl (C2177, above FLT_MAX as a double).
- The file passes `cc -std=c11 -Wall -Wextra -Werror -fsyntax-only`. It produced sha256 `1b6e84c8…`, the
  same on two runs.

`src/xbox360/fp1_pool_primer.c` is **superseded**. Its first 0x68 bytes are a prefix of this layout, and both
FP1 specs match with the PP1 primer instead (below). It is left in place, and the FP1 specs are unchanged.

## Using it in a spec

Add it as the **last** context entry:

```json
"context": ["src/xbox360/<callee>.c", "src/xbox360/pp1_pool_primer.c"]
```

- Any pooled float/double literal in the candidate then gets the original's pool offset. That covers the
  unrelocated `lfs fX, off(rPool)` displacement, which the checker compares bit for bit; the base `lis/addi`
  is still accepted by value (POOL lines).
- Write the constants as plain literals. A value that is not in the original pool is appended after +0xA70,
  or fills the padding hole at +0xa54.
- Listing the primer before another /GL context that introduces new constants shifts the whole pool.
- The named zero constant (FP1 rule, `g_ts4_event_value` at 0x8814B440) is not part of the pool. It still
  comes from the source file's `static const float`.

## Limits

- The primer is a stand-in for whole-program layout, like FP1's first primer and LT1's per-file `flags(/Ob1):`.
  It is context only and is not counted.
- Typing relies on a simple register tracker. An entry reached only through a pointer passed elsewhere, or
  through an indexed load, is typed by the heuristic. All 30 such entries came out as floats, and they
  occupy the same bytes either way. A wrong type would matter only to a function that loads that entry with
  the other width.
- The pool holds no vector constants. The 16-byte `lbl_880D19E0…` objects after it are separate.
- Not run: `tools/matching.py` / `ltcg_route.build`. It uses the same `fn_check_ltcg.verify`, which stubs
  `pp1_pool_f`/`pp1_pool_d` the same way.
